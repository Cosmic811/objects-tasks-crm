# Объекты и задачи

Мини-CRM для строительной компании. Постановщик создаёт объекты, назначает задачи и проверяет результат. Исполнитель видит только свои задачи и отправляет работу на проверку.

Стек: React 19, TypeScript, Vite 8, Supabase Auth, PostgreSQL и RLS. Node.js от 22.18.

Приложение: https://cosmic811.github.io/objects-tasks-crm/

Репозиторий: https://github.com/Cosmic811/objects-tasks-crm

## Настройка Supabase

1. Создайте отдельный Supabase-проект на бесплатном тарифе.
2. Выполните оба SQL-файла из [supabase/migrations](supabase/migrations) по порядку имени в SQL Editor или примените их через Supabase CLI: `supabase link --project-ref YOUR_REF`, затем `supabase db push`. Не выполняйте оба способа для одних миграций.
3. В Authentication → Sign In / Providers отключите **Allow new users to sign up**, сохраните изменения. Оставьте вход Email/Password включённым.
4. В Authentication → Users → Add user создайте подтверждённые аккаунты `manager@crm.example`, `executor1@crm.example`, `executor2@crm.example`. Пароли задайте самостоятельно, передавайте проверяющему приватно.
5. Выполните [seed.sql](supabase/seed.sql). Он назначит роли и создаст три объекта, пять задач во всех пяти статусах и историю. Повторное заполнение блокируется.
6. В Data API оставьте открытой схему public. Схема private не должна входить в exposed schemas.

Дополнительного постановщика можно создать в Auth и добавить его UUID в profiles с ролью manager через SQL Editor. Количество пользователей каждой роли не ограничено одним аккаунтом.

## Локальный запуск

```bash
npm ci
# Скопируйте .env.example в .env.local и заполните URL и публичный ключ.
npm run dev
```

Нужны `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Service role и ключ базы во frontend не требуются. При отсутствии корректной конфигурации приложение показывает инструкцию подключения, без фиктивных данных.

## Проверки

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

`npm test` запускает 76 проверок PostgreSQL: RLS, разрешения, полную матрицу переходов для двух ролей, обязательный комментарий, аудит и мягкое удаление. Контекст Auth в этих тестах локальный.

Для проверки настоящего Supabase API скопируйте `.env.test.example` в `.env.test.local`, укажите доступы созданных тестовых аккаунтов и запустите:

```bash
npm run test:api
```

Сценарий создаёт отдельные тестовые записи, проверяет прямые запросы от разных ролей, полный цикл доработки и конкурентные переходы. В конце скрывает только собственные тестовые записи, сохраняя их аудит. Отчёт записывается в docs/qa/supabase-api.json.

Ручной сценарий: постановщик создаёт объект и задачу, исполнитель берёт её в работу и отправляет на проверку. Постановщик возвращает с комментарием, исполнитель повторяет цикл, постановщик принимает. Затем проверьте историю и попробуйте открыть эту задачу вторым исполнителем.

## Деплой

Подходит любой статический хостинг. Команда сборки `npm run build`, каталог `dist`. Обе публичные переменные Supabase должны быть заданы во время сборки. При размещении в подпапке укажите `VITE_BASE_PATH`, например `/objects-tasks-crm/`.

Workflow GitHub Pages выполняет lint, typecheck, тесты и сборку до публикации. Для него задайте repository variables `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY`, а в Settings → Pages выберите GitHub Actions. Секретные ключи для деплоя не нужны.
